# ADR 007：以 DICOMweb 集成就诊前已有影像

日期：2026-09-26。状态：已采纳。

## 问题

预约原型已有 .NET 业务、测试、Outbox 和小型 FHIR 适配，但缺少可解释的影像互通场景。用户希望贴近医疗软件开发岗位，并沉淀学习和面试资料；时间规模为两周20–30小时，DICOM从零学习。

## 决策

采用“关联已有影像供就诊参考”的用例。Orthanc承担归档和DICOMweb服务；Stone承担渲染。应用新增独立Imaging模块、患者身份映射、预约/Study关系和审计。QIDO找候选，WADO逐实例核验并获取影像；STOW仅用于合成测试数据导入。

使用明确外部PatientID、Issuer和配置来源，缺失或不匹配即拒绝。只开放Scheduler与TaskOperator。查看器走应用同源受限代理，不给浏览器归档凭据。关联和审计原子保存；解除不依赖归档在线，不删除影像，不更改预约版本。

## 未选择的方案

自建PACS/协议服务端会扩大交付范围且偏离.NET业务集成重点；仅展示文件标签缺少预约业务价值；完整检查订单、MWL/MPPS、设备执行结果与FHIR ImagingStudy映射需要额外需求和验证，不在本阶段实现。

## 代价与后续条件

逐请求元数据重验证增加外部调用；当前64MiB响应上限和内存缓冲不适用于大型影像生产负载。身份映射仅单来源预置，没有冲突治理；工作人员授权沿用项目全局范围。真实接入前需设计标识生命周期、流式/缓存策略、真实对象兼容矩阵、网络与数据治理及适用的产品流程。

本项目提供学习和验证证据，不宣称临床部署、完整标准一致性或医疗产品认证。受控代理的公开路径只是所需子集，不能被当作通用DICOMweb服务器。
