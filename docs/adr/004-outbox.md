# ADR 004 — At-least-once delivery and receiver deduplication

A booking transaction commits a full appointment snapshot and immutable MessageId. Worker DI scopes own one DbContext; HTTP runs outside the claim/completion transactions. MySQL `FOR UPDATE SKIP LOCKED` atomically claims an eligible message, increments the attempt count and records a Started attempt. Each claim has a random token and a 30-second lease. HTTP timeout is 5 seconds, so no lease renewal is needed for this bounded request. Completion checks both the token and unexpired lease; a stale process cannot overwrite a reclaimed message. Worker cancellation leaves the lease recoverable. A fifth expired claim becomes Failed, avoiding unlimited crash/reclaim cycles.

Transient HTTP/network errors persist the next attempt time (2^attempt seconds, capped at 300, plus 0–1s jitter). Permanent 4xx except 408/429 fail immediately. Five attempts require Admin intervention. Manual retry keeps MessageId and all attempt rows, resets the current cycle counter, appends an audit, and is itself idempotent. Started without a final outcome means the process may have stopped before its completion transaction; it does not mean no remote effect occurred.

The separate Node 24 receiver uses SQLite WAL on a Docker volume. Its single transaction inserts a MessageId receipt and conditionally applies a newer version snapshot. An old snapshot cannot overwrite a newer cancellation. Both receipts and effects survive restarts. Node's built-in SQLite API is experimental in this pinned runtime; this small mock is an integration test fixture, not a production interoperability service. The shared integration key is loaded from .env, never source-controlled. Fault controls are only enabled in isolated tests with MOCK_CONTROL=true; normal Compose does not enable them.

This is at-least-once transport plus durable receiver deduplication, not end-to-end exactly-once. Real deployments need key rotation, capacity controls, observability, retention and backup policies. Java comparison: HostedService is a lifecycle-managed loop; per-iteration scopes avoid reusing a singleton DbContext. CancellationToken is cooperative cancellation and is passed through database/HTTP/waits; it is not Thread.interrupt.
