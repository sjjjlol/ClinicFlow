# ADR 002 — Same-origin cookie authentication

Use ASP.NET Core cookie authentication, framework PasswordHasher, HttpOnly / SameSite=Strict session cookies and ASP.NET antiforgery tokens on all writes including login/logout. React uses a same-origin proxy; there is no cross-origin credential policy. Production cookies require HTTPS, local development uses HTTP on loopback only. Login is rate limited per client IP (30/minute). Demo account passwords are generated in ignored .env and hashed once during initial seeding; changing .env does not rotate existing hashes. Self-service registration was added in ADR 005; no recovery/SSO.

Roles: staff may read all appointments. Booker reads only its bound patient and appointments, and may create/reschedule/cancel its own appointments before they start. Scheduler manages all bookings, confirmation and completion; only TaskOperator may complete prerequisite tasks, only Admin may retry integration. Admin does not implicitly perform other roles' business writes. Antiforgery tokens are refreshed after identity changes. Authentication/authorization execute before antiforgery validation. The browser displays role-specific actions but the API is authoritative.

Java comparison: cookie middleware corresponds to a security filter pipeline, policies to method/endpoint authorization; the antiforgery service is independent of authentication. DataProtection keys must be persisted/shared if scaling beyond the local demo.
